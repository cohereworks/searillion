# External audit reconciliation — 2026-11-04

The three reported findings are useful, but they are **not three newly
unfixed implementation bugs**. Keep provenance separate from current
observed behavior.

## 1. “A second universe corrupts earlier ones (2×2 reports 512)”

**Historical bug confirmed; current wrapper guards it.**

Graphillion has a process-global universe. The original independent
`RelationUniverse` abstraction wrongly implied independent backend mappings;
a 2×2 family could be addressed through a replacement 3×3 universe and
appear to have 512 members. R5 records the bug and its correction;
R6 introduced a shared multi-signature `RelationWorkspace`.

The current wrapper stamps each compilation with a generation and checks
the generation before family operations. The explicit regression test
`test_second_larger_universe_cannot_make_2x2_report_3x3_cardinality`
verifies 2×2 first reports 16, a newer 3×3 reports 512, and reuse of the
old family **raises** instead of returning 512. Tests also guard
workspace replacement and simultaneous safe signatures.

**Residual risk:** Direct calls to Graphillion's global
`GraphSet.set_universe()` outside Searillion are *not* observable by the
local generation counter. Searillion cannot promise protection against
uncoordinated external Graphillion API use in the same process. The workspace
isolation design needs an explicit process-level owner or backend refactor
before such mixed use is supported.

## 2. “R1 was an artifact of variable ordering”

**Confirmed and already explicitly corrected in R2.**

R1 faithfully preserves the original expensive encoding measurements.
R2 demonstrated that the same n=11 total-function family moved from
~26.64 s / ~4.5 GiB to ~0.039 s / ~30 MiB by changing atom ordering.
The proper interpretation is that **the observed cliff was principally
an ordering pathology**, not an intrinsic limit of ZDD representation.
Do not erase R1; link readers directly to R2's superseding explanation.

This is a central research result, not a minor footnote: variable ordering
belongs in the compilation model and every benchmark's metadata.

## 3. “Asana-recorded M1 code is not in the repo”

**Unresolved provenance/delivery gap, not an established passing feature.**

A search of current repository content, reachable Git history, and named
branches did not identify an M1 source artifact or an M1 identifier.
The connected Asana project listing returned no projects; advanced task
search was unavailable under the connected plan. Therefore we cannot
independently verify what M1 promised, whether its code was written, where
it lives, or whether it was superseded.

**Disposition:** No implementation-complete credit for M1. Record the gap
in the repository tracker, request the original M1 task/provenance when
available, then reconcile deliverables against versioned code and tests.
Do not infer a feature specification from the opaque label “M1.”

## Why this is separate from L001

An audit establishes historical truth and missing provenance; a lab
experiment must articulate a falsifiable hypothesis, protocol, measurement,
and interpretation. L001 follows that latter format. R5/R2 corrections
remain visible in the research ledger, which is not rewritten retroactively.
